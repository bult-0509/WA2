# WEMOVE SPORTS 大模型辅助开发说明

## 文档用途

本说明用于课程验收，介绍大模型在 WEMOVE SPORTS 公司宣传网站开发中的参与方式。文中提示词按项目最终形成的决策链重新整理，重点说明提示词怎样从宽泛要求逐轮收敛为可执行任务，并非聊天记录的逐字还原。

本项目中，大模型承担了需求归纳、方案比较、代码草拟、界面检查、演示数据制作和文档整理等辅助工作。项目范围、技术栈、功能取舍、数据边界和最终验收标准仍由开发者确定；模型给出的内容必须经过构建、数据库操作、接口请求和浏览器页面验证后才能进入交付版本。

## 一 项目中的人机分工

开发者先确定项目目标：把原有公司宣传网站改造成可持续维护的全栈网站，第一阶段实现官网展示、商品管理和咨询处理闭环。随后把口播转录、课程要求和运行环境作为输入交给大模型，让模型整理候选功能与技术方案。开发者保留最终决定权，并在每轮输出后检查是否偏离课程范围。

大模型适合快速处理重复而有规则的工作，例如把需求转成数据字段、补齐接口异常路径、整理中英文固定文案、生成演示商品资料、检查遗漏项。登录安全、数据库事务、权限划分和发布条件等内容不能只依赖文字判断，因此都需要实际运行验证。

| 工作环节 | 大模型提供的辅助 | 开发者负责的决定与验证 |
| --- | --- | --- |
| 需求理解 | 从转录中提取角色、流程和功能候选 | 确定第一阶段边界，排除支付、订单等后续功能 |
| 技术设计 | 给出前后端分层、数据表和接口草案 | 选择 Next.js、NestJS、PostgreSQL 并确认模块关系 |
| 页面实现 | 草拟页面结构、双语文案和交互状态 | 检查品牌表达、可用性和移动端效果 |
| 数据准备 | 整理商品字段并生成演示图片提示词 | 确定数量、类别、发布条件和演示数据声明 |
| 工程验证 | 建议类型检查、构建、接口和浏览器检查项 | 运行命令、观察页面、判断结果是否可交付 |

## 二 提示词微调采用的循环

这里所说的“微调”是对提示词和任务上下文的逐轮修正，不涉及重新训练模型或修改模型权重。每轮只解决一个主要不确定点，上一轮结果会变成下一轮的约束。

第一轮写清目标和使用场景，让模型知道项目为公司宣传网站及课程验收服务。第二轮补充输入和输出，明确需要读取哪些资料、修改哪些模块、形成哪些文件。第三轮加入业务边界与技术限制，例如仅支持中英文、后台需要权限控制、演示商品不冒充企业真实资料。第四轮把“完成”改写成可检查的条件，包括产品数量、字段完整性、接口状态、构建结果和页面表现。第五轮根据运行反馈继续收窄问题，只让模型处理已经暴露的缺陷。

| 轮次 | 提示词增加的内容 | 对输出的影响 |
| --- | --- | --- |
| 目标轮 | 项目对象、受众、希望解决的问题 | 避免只做静态页面或偏离公司宣传场景 |
| 边界轮 | 当前阶段要做与暂缓的业务 | 控制工作量，避免提前实现支付和订单 |
| 约束轮 | 技术栈、语言、数据、安全和环境条件 | 让代码可以进入现有工程而非另起项目 |
| 验收轮 | 数量、状态码、命令和页面检查方法 | 把“看起来完成”转成可复核证据 |
| 反馈轮 | 实际报错、截图或失败条件 | 针对真实问题修正，不凭猜测扩大改动 |

## 三 从宽泛要求到可执行提示词

以下提示词是为了说明调整方法而整理的示例。每组先保留一个宽泛起点，再展示怎样加入上下文、约束和验收条件。

### 1 需求范围的收敛

宽泛要求可以写成“分析材料并做一个公司网站”。它没有说明用户角色、业务流程和阶段边界，模型容易把宣传页、商城和内部系统混在一起。

整理后的提示词：

> 阅读口播转录和课程要求，把需求按网站访客、后台人员、系统三个角色整理。第一阶段只覆盖公司宣传、商品目录、商品详情、联系咨询、后台商品维护、咨询处理、首页文案和审计记录。支付、订单、经销商申请与正式部署列为后续范围。输出功能清单、数据流和可验证的验收条件。

这次调整把任务对象从“网站”改成三类参与者及两条核心业务流程。开发时可以逐项追踪，答辩时也能清楚解释当前完成到哪里。

### 2 技术架构的收敛

只要求“使用前后端分离”仍然会留下版本、职责和请求路径不明确的问题。

整理后的提示词：

> 在单仓库中使用 Next.js 16、NestJS 12 和 PostgreSQL 17。浏览器访问 3100 端口，Next.js 负责页面与同源代理，NestJS 在 3101 端口处理校验、权限和业务规则，PostgreSQL保存商品、媒体、人员、会话、询盘、首页内容与审计记录。说明一次请求经过三层的顺序，并保持 API 前缀为 /api/v1。

加入端口、职责和数据对象后，模型生成的目录、环境变量和接口调用能够彼此对应。后续出现问题时，也能判断错误位于页面、代理、API 还是数据库。

### 3 商品发布流程的收敛

“增加商品管理”没有说明草稿、发布条件和数据完整性，很容易得到只含名称与图片的简单增删改查。

整理后的提示词：

> 商品使用 Draft、Active、Archived 三种状态。后台可以创建和修改草稿；发布前必须具备主图、简介、详细描述、安全说明、SEO 信息和至少三条卖点。默认 SKU 独立存放，slug 与 SKU 必须唯一。官网目录只显示 Active，Archived 保留原详情地址。并发修改使用 version 字段拒绝覆盖旧数据，所有后台修改写入审计记录。

这轮加入了状态机、发布门槛、版本控制和审计要求，商品功能由普通表单变成可以解释业务原则的发布流程。

### 4 双语界面的收敛

“添加中文和英文”没有界定翻译范围与偏好保存方式，也没有处理服务端首屏和客户端切换的一致性。

整理后的提示词：

> 官网和后台只支持 English 与中文。固定界面文字使用统一词汇映射；语言选择写入 wm_locale Cookie，刷新和跨页面后仍然保留；服务端首屏根据 Cookie 设置 html lang，客户端切换后刷新服务端组件。商品业务值保持稳定，只在显示层翻译分类、使用环境和错误提示。检查按钮状态、辅助技术标签与移动端导航。

改进后的提示词给出了数据层与显示层的边界，避免为了翻译而改变数据库枚举，也减少了首屏语言和切换后语言不一致的问题。

### 5 演示商品与图片生成的收敛

“生成数十个产品并上架”仍缺少准确数量、分类比例、视觉统一和商品字段要求。

整理后的提示词：

> 制作 24 件课程演示商品，保龄、平衡协调、户外游戏各 8 件。每件商品需要唯一 slug、SKU、名称、简介、详细玩法、四条卖点、适龄范围、使用环境、安全说明、规格、SEO 字段和图片替代文字。为每件商品单独生成 1:1 棚拍成品图，统一暖白背景与蓝、珊瑚红、黄色、青绿色、原木色，不出现人物、品牌标识、水印或图片文字。图片转为 WebP 后由幂等脚本写入媒体表并把商品发布为 Active。

这一轮把“数十个”落实为可计数的 24 件，并把图片风格、无障碍说明和数据库状态连在一起。模型输出随后还要接受唯一性检查、图片解码检查和公开媒体请求验证。

### 6 跨设备运行问题的收敛

最初问题是“其他设备运行批处理时缺少 env file”。如果只复制模板，会留下默认口令或导致已有数据库与新环境文件不一致。

整理后的提示词：

> 修改 Windows 启动流程。当根目录缺少 .env 时，用 Windows PowerShell 5.1 可运行的加密随机数 API 生成 64 位十六进制数据库口令和 APP_KEY，不输出到终端，也不提交版本库。若检测到本项目已有 PostgreSQL 数据目录和管理员口令，则启动该实例并同步 wemove 角色口令；全新设备缺少 PostgreSQL 时给出明确初始化提示。已有 .env 保持不覆盖。

提示词经过补充后同时覆盖首次克隆、误删环境文件和已有数据库三种情况。实现完成后需要在临时目录验证文件生成，再在现有项目中验证数据库仍可连接。

### 7 代码注释要求的收敛

“代码注释超过三分之一”容易产生两种问题：统计口径不明确，或者为了比例加入重复代码含义的无效注释。

整理后的提示词：

> 统计 apps、scripts、data、database/migrations 和根目录 start.bat 中的项目自有源码，排除依赖、构建产物、框架生成文件和检查脚本自身。空行不参与分母，纯注释行计作注释，比例按注释行除以注释行与代码行之和计算。为各模块补充职责、输入、输出、三步流程、约束、失败处理、维护提示和验证重点，避免逐行复述语法。新增 npm run check:comments，低于 33.33% 时返回失败退出码。

调整后的要求既能被机器检查，也限定了注释内容。当前结果为 640 行注释、1182 行代码，共 1822 行非空源码，注释率 35.13%。已执行的数据库迁移保持原文不变，避免破坏迁移校验和。

## 四 反馈如何进入下一轮

提示词微调不能只在编写代码前进行。商品图片首次接入后，数据库中已经有媒体记录，但浏览器请求仍返回 500。把“中文路径下 Express sendFile 读取失败、同一文件用 Node readFile 可以读取”作为新证据加入提示词后，修正范围被限定在媒体响应方法，最终改为读取 Buffer 后发送，24 张图片均返回 image/webp 和 200 状态。

文档排版也采用同样方法。初稿导出后出现最后一句单独占一页的问题。下一轮不再要求重写全文，只提供“第 10 页仅有一段收尾文字”的反馈，让调整集中在冗余收尾段，重新导出后回到 9 页。反馈必须具体到可观察现象，模型才容易给出范围合适的修正。

## 五 输出审查与验收

模型生成代码后依次进行静态检查、构建检查、数据检查和页面检查。`npm run typecheck` 验证前后端类型，`npm run build` 验证生产构建，`npm run check:runtime` 检查 Web、API 和数据库，`npm run test:catalog` 以真实数据库覆盖目录业务的正常与异常路径。商品种子脚本连续执行两次，数据库仍保持 24 件商品；24 个媒体地址逐一检查为可访问状态。

界面检查关注目录分页、商品详情、英汉切换、表单错误、后台登录和移动端布局。文档则导出为 PDF 后逐页查看，确认没有文字裁切、表格溢出和异常空白页。只有自动检查和人工观察都通过，才把结果提交到版本库。

新增的注释率检查采用同样原则。它输出每个文件的注释行、代码行和比例，最终以整体比例作为课程要求的门槛。该结果可以重复运行，不依赖人工估算。

## 六 使用大模型时保留的边界

演示商品名称、玩法和规格由模型辅助整理，用于课程演示，不代表 WEMOVE SPORTS 已确认的真实 SKU、材质或安全承诺。正式上线前仍需企业逐项审核。生成式商品图片同样只用于界面和流程演示。

安全功能不能因为模型给出代码就视为可靠。本项目用参数化查询、服务端权限、TOTP 重放保护、CSRF 检查、限流、版本冲突和审计记录建立第一阶段边界，但生产环境仍需要正式账号恢复、密钥管理、监控、备份和部署审查。

大模型在本项目中的价值主要是缩短从模糊需求到可运行原型的距离。效果取决于提示词是否给出清楚上下文、约束、验收条件和真实反馈。开发者需要持续判断范围、运行结果与风险，不能把模型输出直接当作验收结论。

## 七 可复用的提示词模板

后续类似任务可以沿用以下结构：

> 项目背景：说明系统对象、使用者和当前阶段。任务目标：写出本轮唯一的主要结果。已有输入：列出文件、接口、报错或截图。必须满足：给出技术栈、数据规则、安全限制和不能改动的边界。完成标准：列出可以运行的命令、数量、状态码和页面现象。输出要求：说明要修改的文件与文档形式。反馈规则：若验证失败，先报告具体证据，再围绕失败点调整，不扩大无关范围。

这个模板不追求一次写出很长的指令。实际使用时先填最必要的信息，观察输出和运行结果，再逐轮补充缺少的条件。每一轮都应留下可检查的变化，使提示词调整与工程验证形成闭环。
